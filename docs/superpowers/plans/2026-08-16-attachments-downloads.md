# Attachments and Downloads

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Downloading an attachment stays inside the app: the download runs under a `WKDownload`, shows progress once it is worth showing, lands somewhere findable, and previews with Quick Look. Today the download decision hands the URL to the default browser, which bounces the user out of the app — and worse, on iOS a viewable attachment (a PDF) navigates the main frame itself: the chromeless shell then shows the document with no back affordance at all, and the only way back to the mailbox is killing the app. The official Fastmail app presents such documents in a viewer with a back button top-left and a share button top-right; `QLPreviewController` provides exactly that chrome.

**Architecture:** `NavigationPolicy.decideResponse` already computes the decision (`Content-Disposition: attachment` or an unshowable MIME type → download; everything else stays in Fastmail's own viewer). `WebCoordinator` — already the navigation and UI delegate, and the established place for delegate surface (the JavaScript dialogs live there) — answers `.download` and hands the `WKDownload` to a new `DownloadManager`, the `WKDownloadDelegate`. Progress and completed items publish through an observable model; the iOS surface reuses the `ShellModel` overlay mechanism rather than inventing a second one. Settings extend the existing surfaces: the macOS `Settings` scene and the iOS `Settings.bundle` (regenerated by its generator, guarded by the existing bundle-versus-catalog test pattern).

**Tech Stack:** WebKit (`WKDownload`, `WKDownloadDelegate`), `Progress`, QuickLook (`QLPreviewPanel` / `QLPreviewController`), `UTType`, security-scoped bookmarks (macOS custom folder only), Swift Testing.

## Global Constraints

- No code comments. Ship bare code.
- Swift 6 strict concurrency. No third-party dependencies.
- Never add `WKAppBoundDomains` to any Info.plist.
- Package tests use Swift Testing; `Tests/IntegrationTests` uses XCTest.
- On macOS, Fastmail keeps rendering what it can render: only `Content-Disposition: attachment` and unshowable MIME types become downloads, because the desktop layout previews attachments in its own in-page overlay and no main-frame navigation happens. On iOS the mobile layout navigates the main frame to `fastmailusercontent.com` instead, and a chromeless shell showing a bare document is a trap — so there, any main-frame navigation to attachment content becomes a download and previews in Quick Look, whose Done and share buttons are the chrome the mailbox needs to come back.
- The auto-open allowlist is fixed in code, matched by `UTType.conforms(to:)`, never by file extension, and never user-editable — a widenable allowlist is a phishing vector in a mail client.

### Task 1: `DownloadManager` and the model

**Files:**
- Create: `Packages/FastmailShellKit/Sources/FastmailShellKit/DownloadManager.swift`
- Test: `Packages/FastmailShellKit/Tests/FastmailShellKitTests/DownloadManagerTests.swift`

**Interfaces:**
- Produces: `DownloadItem` (`id`, `filename`, `progress`, `state: active|finished|failed|cancelled`, `fileURL?`); `DownloadManager: NSObject, WKDownloadDelegate, ObservableObject` with `@Published var items: [DownloadItem]`; `func adopt(_ download: WKDownload)`.

- [ ] **Step 1:** Destination policy. macOS: `~/Downloads` via the `com.apple.security.files.downloads.read-write` entitlement; a custom folder, when set, resolves from a security-scoped bookmark and falls back to `~/Downloads` with a one-time report when resolution fails. iOS: the app's Documents directory. Filename collisions get ` (2)`, ` (3)` suffixes before the extension.
- [ ] **Step 2:** Nothing publishes for the first 500ms of a download — most attachments finish inside the window and a flashed panel for a 40 KB file is worse than nothing. Past it, the item appears with `Progress` (use `localizedAdditionalDescription` for byte text; unknown totals render indeterminate).
- [ ] **Step 3:** Failure and cancellation remove the partial file and surface once through the banner. Completed items stay listed for the session only.
- [ ] **Step 4:** Unit tests: collision suffixing, threshold (a download finishing in 100ms never publishes), cancellation leaves no file, bookmark failure falls back.

### Task 2: Wire the decision to a real download

**Files:**
- Modify: `WebCoordinator.swift`, `WebContainer.swift`

- [ ] **Step 1:** The `.download` outcome answers `WKNavigationResponsePolicy.download` (and the action-level equivalent for direct download navigations) instead of opening externally. Implement `webView(_:navigationResponse:didBecome:)` / `(_:navigationAction:didBecome:)` and hand the `WKDownload` to the manager.
- [ ] **Step 2:** The iOS trap rule, in `NavigationPolicy` so it stays pure and tested: `decideResponse` learns the frame and host, and a main-frame response from `fastmailusercontent.com` is `.download` on iOS even when `canShowMIMEType` is true. macOS keeps `.allow` for showable types — its desktop layout never navigates for previews. The completed download previews immediately in Quick Look, so a tapped PDF reads as "viewer opened", not "download happened": back button top-left, share top-right, mailbox untouched behind it.
- [ ] **Step 3:** Subframe and non-download cases keep today's behaviour exactly; the existing `WebCoordinatorTests` outcome table extends with the changed mappings, including the iOS main-frame attachment case and the macOS inline case.

### Task 3: Quick Look and auto-open

**Files:**
- Create: `Packages/FastmailShellKit/Sources/FastmailShellKit/AttachmentOpener.swift`
- Modify: `DownloadManager.swift`
- Test: extend `DownloadManagerTests.swift`

- [ ] **Step 1:** A completed download previews with Quick Look (`QLPreviewPanel` on macOS, `QLPreviewController` on iOS) — Quick Look requires a local `file:` URL, which is why the download path exists at all.
- [ ] **Step 2:** Auto-open, off by default: when enabled and the finished file's sniffed type conforms to the fixed allowlist — PDF, plain text, RTF, PNG/JPEG/GIF/HEIC/WebP, `.ics` — it opens in the default application instead of previewing. Archives, disk images, installers, scripts, executables always preview.
- [ ] **Step 3:** Unit tests: allowlist admits PDF and images, refuses `.dmg`/`.zip`/executables, and a spoofed `.pdf` extension on a disallowed sniffed type is still refused.

## Verification

- `make test` green.
- macOS: download an attachment → lands in `~/Downloads`, Quick Look opens on click, cancel works mid-flight on a large file, ring appears only for slow downloads.
- iOS: same flow → file visible in Files under the app, pill appears for a large download, Quick Look previews.
- iOS: tap a PDF attachment in a message → the viewer presents with back top-left and share top-right, dismissing returns to the mailbox exactly where it was, and at no point is the mailbox navigated away. The kill-the-app trap is gone.
- macOS: a PDF opened (not downloaded) inside Fastmail still renders in Fastmail's own viewer.
- Auto-open on: a PDF opens in Preview; a `.zip` still only previews.
